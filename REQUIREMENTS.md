# Требования к проекту CRSF-Display

## 1. Назначение проекта

Разработать встроенное приложение для `M5Stack Basic` на базе `ESP-IDF`, которое:

- принимает данные каналов управления от `ExpressLRS receiver` по последовательному интерфейсу с использованием протокола `CRSF`;
- отправляет телеметрию обратно в приемник по протоколу `CRSF`;
- отображает на встроенном LCD значения входных каналов и данные телеметрии;
- предоставляет `Web UI`, дублирующий экраны LCD и состояние устройства;
- позволяет пользователю переключаться между экраном каналов и экраном телеметрии;
- позволяет задавать источник `GPS`-телеметрии:
  - вручную;
  - от внешнего GPS-приемника;
  - от симулятора GPS-координат.

## 2. Среда разработки

- Основная IDE и SDK: `ESP-IDF`.
- Язык реализации: `C`.
- Система сборки: штатная сборка `ESP-IDF` через `CMake`.

## 3. Аппаратная платформа

### 3.1. Основное устройство

- Целевая платформа: `M5Stack Basic`.
- Должны использоваться:
  - встроенный LCD-дисплей;
  - встроенные кнопки устройства для навигации по экрану и изменения параметров;
  - встроенный слот `SDCard` для хранения `JSON`-файла параметров симуляции;
  - встроенный `Wi-Fi` интерфейс для публикации `Web UI`;
  - аппаратные UART-интерфейсы ESP32.

### 3.2. Подключаемые устройства

- `ELRS receiver`, подключенный к `UART2` контроллера `ESP32` в составе `M5Stack Basic`.
- `M5Stack Mini GPS/BDS Unit (AT6558)` как внешний источник `GPS`-телеметрии.

### 3.3. Аппаратные ограничения и допущения

- Подключение `ELRS receiver` выполняется по TTL UART.
- `ELRS receiver` должен использовать аппаратный `UART2` на линиях `RXD2 = GPIO16` и `TXD2 = GPIO17`.
- Для `M5Stack Basic` эти линии соответствуют `Port C` (`Grove Blue`).
- `M5Stack Mini GPS/BDS Unit (AT6558)` должен использовать программный UART (`software UART`) на линиях `GPIO21` и `GPIO22`.
- Для проекта выбирается следующая привязка `software UART` для GPS:
  - `GPS RX = GPIO21`;
  - `GPS TX = GPIO22`;
- `GPS` и `CRSF` должны использовать разные последовательные интерфейсы.

## 4. Функциональные требования

### 4.1. Прием CRSF

Система должна:

- принимать входящий поток `CRSF` от `ELRS receiver`;
- распознавать и декодировать кадры `RX Channels`;
- распознавать и декодировать кадры `Link Statistics`;
- поддерживать не менее 16 каналов;
- обновлять отображаемые значения каналов на LCD в реальном времени;
- корректно обрабатывать потерю сигнала, ошибки кадра и переподключение приемника.

### 4.2. Передача телеметрии по CRSF

Система должна:

- формировать и отправлять телеметрию обратно в `ELRS receiver` по протоколу `CRSF`;
- поддерживать передачу следующих типов `CRSF telemetry`:
  - `GPS`;
  - `Attitude`;
  - `Barometric Altitude`;
  - `Battery`;
  - `Flight Modes`;
- для `Flight Modes` на первом этапе поддерживать следующий фиксированный набор значений:
  - `Angle Mode`;
  - `Horizon Mode`;
  - `Acro Mode`;
- обеспечивать архитектуру, допускающую последующее добавление других типов телеметрии без переработки базового обмена.

### 4.3. Экран каналов

На основном экране должны отображаться:

- значения каналов со следующими именами:
  - `Ail`;
  - `Elv`;
  - `Thr`;
  - `Roll`;
  - `Aux1`;
  - `Aux2`;
  - `Aux3`;
  - `Aux4`;
  - `Aux5`;
  - `Aux6`;
  - `Aux7`;
  - `Aux8`;
  - `Aux9`;
  - `Aux10`;
  - `Aux11`;
  - `Aux12`;
- признак наличия или отсутствия CRSF-связи;
- частота обновления или индикатор активности потока данных.

Требования к экрану:

- значения каналов должны отображаться в нормализованном виде;
- отображение сырых значений `CRSF` не требуется;
- значения должны быть читаемыми на экране `M5Stack Basic`;
- обновление экрана не должно мешать стабильному приему и передаче `CRSF`.

### 4.4. Экран Link Statistics

Для отображения качества радиолинии должен быть реализован отдельный экран `Link Statistics`.

На этом экране пользователь должен иметь возможность:

- просматривать текущие статистические данные входящего `CRSF`-линка;
- видеть состояние обновления статистики в реальном времени;
- переключать страницы или прокручивать список статистики, если все поля не помещаются на одном экране.

На экране должны отображаться следующие поля:

- `Uplink RSSI Antenna 1` в формате `dBm * -1`;
- `Uplink RSSI Antenna 2` в формате `dBm * -1`;
- `Uplink Link Quality/Packet Success Rate` в процентах;
- `Uplink Signal-to-Noise Ratio` в `dB`;
- `Active Antenna`:
  - `0 = Antenna 1`;
  - `1 = Antenna 2`;
- `RF Mode`:
  - `4 fps = 0`;
  - `50 fps = 1`;
  - `150 fps = 2`;
  - `250 fps = 3`;
  - `500 fps = 4`;
  - `1000 fps = 5`;
- `Uplink TX Power`:
  - `0 mW = 0`;
  - `10 mW = 1`;
  - `25 mW = 2`;
  - `100 mW = 3`;
  - `250 mW = 4`;
  - `500 mW = 5`;
  - `1000 mW = 6`;
  - `2000 mW = 7`;
- `Downlink RSSI` в формате `dBm * -1`;
- `Downlink Link Quality/Packet Success Rate` в процентах;
- `Downlink Signal-to-Noise Ratio` в `dB`.

Требования к экрану:

- экран должен отображать как числовое значение, так и расшифровку для `Active Antenna`, `RF Mode` и `Uplink TX Power`;
- при нехватке места на LCD допускается разбиение экрана на несколько страниц внутри одного логического экрана;
- отсутствие свежих кадров `Link Statistics` должно отображаться как диагностический статус.

### 4.5. Экран телеметрии

Экран телеметрии должен быть отдельным экраном обзора и состояния.

На этом экране пользователь должен иметь возможность:

- выбрать активный источник GPS-телеметрии;
- просматривать текущие телеметрические значения;
- видеть статус источника GPS-телеметрии;
- перейти к редактированию ручных параметров;
- перейти к экрану параметров симуляции;
- перейти к экрану статуса GPS-приемника.

Минимально должны отображаться следующие параметры:

- активный источник GPS-телеметрии;
- состояние передачи телеметрии по `CRSF`;
- блок `GPS`:
  - широта;
  - долгота;
  - GPS-высота;
  - скорость;
  - курс;
  - количество спутников;
  - признак валидности GPS-фикса;
- блок `Attitude`:
  - `Pitch`;
  - `Roll`;
  - `Yaw`;
- блок `Barometric Altitude`:
  - барометрическая высота;
- блок `Battery`:
  - напряжение;
  - ток;
- блок `Flight Modes`:
  - текущее имя режима полета;

### 4.6. Экран параметров симуляции

Для режима симулятора должен быть реализован отдельный экран параметров симуляции.

На этом экране пользователь должен иметь возможность:

- задавать стартовую широту;
- задавать стартовую долготу;
- задавать высоту;
- задавать скорость движения;
- задавать курс;
- задавать интервал обновления координат;
- задавать шаг изменения координат или использовать расчет по скорости и времени;
- включать и отключать валидный GPS-фикс;
- задавать количество спутников;
- запускать, ставить на паузу и останавливать симуляцию;
- сбрасывать координаты симуляции к стартовым значениям;
- выбирать активный профиль симуляции;
- сохранять текущие параметры симуляции в `JSON`-файл на `SDCard`;
- загружать параметры симуляции из `JSON`-файла на `SDCard`.

Требования к экрану:

- все параметры симуляции должны редактироваться с кнопок `M5Stack Basic`;
- текущий статус симуляции должен быть виден на экране;
- последние сохраненные параметры симуляции должны восстанавливаться после перезапуска устройства, если `JSON`-файл доступен;
- должно поддерживаться хранение нескольких `JSON`-профилей симуляции на `SDCard`;
- на экране должен отображаться статус операций `Save JSON` и `Load JSON`;
- при отсутствии `SDCard` или ошибке чтения/записи пользователь должен видеть диагностическое сообщение.

### 4.7. Источники телеметрии

Выбор источника относится к блоку `GPS` в составе общей телеметрии.

На первом этапе:

- блок `GPS` должен заполняться из одного из трех источников: `Manual`, `External GPS`, `Simulator`;
- блоки `Attitude`, `Barometric Altitude`, `Battery` и `Flight Modes` должны задаваться вручную и передаваться независимо от выбранного GPS-источника.
- для блока `Flight Modes` должны использоваться только значения `Angle Mode`, `Horizon Mode`, `Acro Mode`.

#### 4.7.1. Ручной ввод

Система должна позволять вручную задавать телеметрические параметры через интерфейс устройства.

Минимальные требования:

- редактирование числовых значений на экране;
- выбор редактируемого поля кнопками устройства;
- отображение текущего набора редактируемых параметров;
- ручной ввод значений для:
  - `GPS`;
  - `Attitude`;
  - `Barometric Altitude`;
  - `Battery`;
  - `Flight Modes`;
- сохранение последних установленных значений между перезапусками.

#### 4.7.2. Внешний GPS-приемник

Система должна поддерживать получение координат и сопутствующих параметров от `M5Stack Mini GPS/BDS Unit (AT6558)`.

Минимальные требования:

- подключение через программный UART (`software UART`);
- использование выбранных линий `GPS RX = GPIO21` и `GPS TX = GPIO22`;
- прием данных по последовательному интерфейсу с параметрами по умолчанию `9600 8N1`;
- использование формата данных `NMEA 0183`;
- обязательный разбор сообщений:
  - `GGA`;
  - `RMC`;
- дополнительный разбор сообщений для экрана `GPS Status`:
  - `GSA`;
  - `GSV`;
- парсинг координат, скорости, курса, высоты и числа спутников;
- отображение статуса приема данных и валидности GPS-фикса;
- обновление только блока `GPS` в составе общей телеметрии;
- передача этих данных в виде `CRSF telemetry`.

#### 4.7.3. Симулятор GPS-координат

Система должна поддерживать режим генерации GPS-данных без внешнего приемника.

Минимальные требования:

- задание стартовых координат;
- задание скорости перемещения;
- задание курса;
- автоматическое обновление координат во времени;
- возможность запуска, паузы и остановки симуляции;
- обновление только блока `GPS` в составе общей телеметрии;
- передача сгенерированных координат в `CRSF telemetry`.

### 4.8. Переключение режимов

Система должна:

- позволять переходить с экрана каналов на экран `Link Statistics` и экран телеметрии кнопками `M5Stack`;
- позволять переходить с экрана `Link Statistics` на экран телеметрии;
- позволять переходить с экрана телеметрии на экран ручного ввода, экран параметров симуляции и экран статуса GPS;
- позволять переключать источник GPS-телеметрии без перезагрузки устройства;
- гарантировать, что в каждый момент времени активен только один источник GPS-телеметрии.

### 4.9. Web UI

Система должна предоставлять встроенный `Web UI`, который:

- доступен по `Wi-Fi`;
- дублирует логические экраны LCD;
- использует общее состояние приложения с LCD-интерфейсом;
- обеспечивает более удобную работу с параметрами и диагностикой.

Минимальные требования к `Web UI`:

- доступ к `Web UI` должен быть доступен как минимум в режиме собственной точки доступа `SoftAP`;
- отображение экрана каналов `CRSF`;
- отображение экрана `Link Statistics`;
- отображение экрана обзора телеметрии;
- отображение экрана ручного ввода телеметрии;
- отображение экрана параметров симуляции;
- отображение экрана статуса GPS;
- выбор активного источника GPS-телеметрии;
- редактирование ручной телеметрии;
- редактирование параметров симуляции;
- выбор активного `JSON`-профиля симуляции;
- выполнение команд `Start`, `Pause`, `Stop`, `Reset`, `Save JSON`, `Load JSON`.

Требования к удобству `Web UI`:

- все основные параметры должны быть доступны без постраничного пролистывания, если это возможно на веб-странице;
- для числовых полей должны использоваться удобные формы ввода;
- для перечислимых значений должны использоваться списки выбора;
- `Link Statistics` должны отображаться в более компактном и удобном виде, чем на LCD;
- изменения, внесенные через `Web UI`, должны немедленно отражаться на LCD, и наоборот, через общее состояние приложения.

## 5. Пользовательский интерфейс

### 5.1. Управление

Пользовательский интерфейс должен быть рассчитан на управление встроенными кнопками `M5Stack Basic`.

Минимальный набор действий:

- переход между экранами;
- перемещение по пунктам меню;
- вход в режим редактирования;
- изменение значения параметра;
- подтверждение и отмена изменения.

### 5.2. Перечень экранов

Логический пользовательский интерфейс должен состоять минимум из следующих экранов:

1. Экран каналов `CRSF`.
2. Экран `Link Statistics`.
3. Экран обзора телеметрии.
4. Экран ручного ввода телеметрии.
5. Экран параметров симуляции.
6. Экран статуса внешнего GPS-приемника.

Эти экраны должны быть доступны на LCD и в `Web UI`.

### 5.3. Описание экранов

#### 5.3.1. Экран каналов `CRSF`

Назначение экрана:

- отображение текущих значений каналов управления;
- отображение состояния приема `CRSF`;
- предоставление быстрого перехода к телеметрическим экранам.

На экране должны быть:

- значения каналов `Ail`, `Elv`, `Thr`, `Roll`, `Aux1...Aux12`;
- индикатор активности приема;
- индикатор ошибки кадра или отсутствия связи;
- краткий статус передачи телеметрии.

#### 5.3.2. Экран `Link Statistics`

Назначение экрана:

- отображение статистики качества радиолинии `CRSF`;
- отображение диагностических параметров uplink/downlink;
- предоставление перехода к экрану обзора телеметрии.

На экране должны быть:

- `Uplink RSSI Antenna 1`;
- `Uplink RSSI Antenna 2`;
- `Uplink Link Quality/Packet Success Rate`;
- `Uplink Signal-to-Noise Ratio`;
- `Active Antenna`;
- `RF Mode`;
- `Uplink TX Power`;
- `Downlink RSSI`;
- `Downlink Link Quality/Packet Success Rate`;
- `Downlink Signal-to-Noise Ratio`;
- индикатор актуальности статистики или времени последнего обновления.

#### 5.3.3. Экран обзора телеметрии

Назначение экрана:

- отображение текущих телеметрических данных;
- выбор активного источника GPS-телеметрии;
- навигация к специализированным экранам настройки.

На экране должны быть:

- активный источник GPS-телеметрии;
- сводные значения блока `GPS`;
- сводные значения блока `Attitude`;
- сводные значения блока `Barometric Altitude`;
- сводные значения блока `Battery`;
- текущее значение блока `Flight Modes`;
- статус отправки `CRSF telemetry`.

#### 5.3.4. Экран ручного ввода телеметрии

Назначение экрана:

- ввод и редактирование телеметрических значений вручную.

На экране должны быть:

- список редактируемых телеметрических полей для `GPS`, `Attitude`, `Barometric Altitude`, `Battery`, `Flight Modes`;
- выделение текущего поля;
- текущие и редактируемые значения;
- для `Flight Modes` выбор значения из списка `Angle Mode`, `Horizon Mode`, `Acro Mode`;
- элементы подтверждения или отмены изменения.

#### 5.3.5. Экран параметров симуляции

Назначение экрана:

- настройка генератора GPS-координат;
- управление запуском симуляции.

На экране должны быть:

- стартовая широта;
- стартовая долгота;
- высота;
- скорость;
- курс;
- интервал обновления;
- количество спутников;
- флаг валидного GPS-фикса;
- статус симуляции: `Stopped`, `Running`, `Paused`;
- имя или путь активного профиля симуляции;
- команды запуска, паузы, остановки, сброса, `Save JSON` и `Load JSON`;
- путь к активному `JSON`-файлу профиля симуляции;
- статус последней операции чтения/записи на `SDCard`.

#### 5.3.6. Экран статуса внешнего GPS-приемника

Назначение экрана:

- отображение состояния внешнего GPS-приемника;
- диагностика входящих GPS-данных.

На экране должны быть:

- состояние подключения GPS;
- наличие входящего потока данных;
- тип используемого протокола GPS;
- широта и долгота;
- скорость;
- курс;
- высота;
- число спутников;
- валидность GPS-фикса;
- время последнего успешного обновления.

### 5.4. Навигация между экранами

Минимальная логика навигации должна быть следующей:

- экран каналов является стартовым основным экраном;
- с экрана каналов пользователь может перейти на экран `Link Statistics` и на экран обзора телеметрии;
- с экрана `Link Statistics` пользователь может перейти на экран обзора телеметрии или вернуться на экран каналов;
- с экрана обзора телеметрии пользователь может перейти:
  - на экран ручного ввода, если выбран ручной источник;
  - на экран параметров симуляции, если выбран источник симуляции;
  - на экран статуса GPS, если выбран внешний GPS;
- из любого экрана настройки пользователь должен иметь возможность вернуться на экран обзора телеметрии;
- из экрана обзора телеметрии пользователь должен иметь возможность вернуться на экран каналов.

### 5.5. Схема меню

Минимальная схема меню должна быть следующей:

1. `CRSF Channels`
2. `Link Statistics`
3. `Telemetry Overview`
4. `Manual Telemetry`
5. `Simulation Parameters`
6. `GPS Status`

Логика входа в пункты меню должна быть следующей:

- `CRSF Channels` является стартовым экраном после загрузки;
- `Link Statistics` открывается из `CRSF Channels`;
- `Telemetry Overview` открывается из `CRSF Channels` или из `Link Statistics`;
- `Manual Telemetry` открывается из `Telemetry Overview`, если выбран источник `Manual`;
- `Simulation Parameters` открывается из `Telemetry Overview`, если выбран источник `Simulator`;
- `GPS Status` открывается из `Telemetry Overview`, если выбран источник `External GPS`.

Логика возврата должна быть следующей:

- из `Link Statistics` возврат выполняется на `CRSF Channels`;
- из `Manual Telemetry`, `Simulation Parameters` и `GPS Status` возврат выполняется на `Telemetry Overview`;
- из `Telemetry Overview` возврат выполняется на `CRSF Channels`.

### 5.6. Назначение кнопок

Для `M5Stack Basic` должны использоваться три кнопки:

- `Btn A` левая кнопка;
- `Btn B` центральная кнопка;
- `Btn C` правая кнопка.

В режиме просмотра экранов назначение кнопок должно быть единым:

- `Btn A`: назад или предыдущий экран, а если возврат недоступен, то локальное действие экрана или отсутствие действия;
- `Btn B`: вход, подтверждение выбора или переход в режим редактирования;
- `Btn C`: следующий экран, следующий пункт или быстрое действие для текущего экрана.

В режиме редактирования параметров назначение кнопок должно быть следующим:

- `Btn A`: уменьшить значение или отменить редактирование;
- `Btn B`: подтвердить изменение и при необходимости перейти к следующему полю;
- `Btn C`: увеличить значение или переключить состояние параметра.

### 5.7. Поведение кнопок по экранам

#### 5.7.1. Экран каналов `CRSF`

- `Btn A`: без действия или открытие краткого статуса связи.
- `Btn B`: переход на `Telemetry Overview`.
- `Btn C`: переход на `Link Statistics`.

#### 5.7.2. Экран `Link Statistics`

- `Btn A`: возврат на `CRSF Channels`.
- `Btn B`: переход на `Telemetry Overview`.
- `Btn C`: переключение страницы статистики или детализации отображения.

#### 5.7.3. Экран обзора телеметрии

- `Btn A`: возврат на `CRSF Channels`.
- `Btn B`: вход в экран, соответствующий выбранному источнику GPS-телеметрии.
- `Btn C`: переключение активного источника `Manual -> External GPS -> Simulator -> Manual`.

#### 5.7.4. Экран ручного ввода телеметрии

В режиме просмотра:

- `Btn A`: возврат на `Telemetry Overview`.
- `Btn B`: вход в редактирование выбранного поля.
- `Btn C`: переход к следующему редактируемому полю.

В режиме редактирования:

- `Btn A`: уменьшение значения или отмена редактирования.
- `Btn B`: подтверждение значения.
- `Btn C`: увеличение значения.

#### 5.7.5. Экран параметров симуляции

В режиме просмотра:

- `Btn A`: возврат на `Telemetry Overview`.
- `Btn B`: вход в редактирование выбранного параметра или выполнение команды `Start/Pause/Stop/Save JSON/Load JSON`.
- `Btn C`: переход к следующему параметру или команде.

В режиме редактирования:

- `Btn A`: уменьшение значения или отмена редактирования.
- `Btn B`: подтверждение значения.
- `Btn C`: увеличение значения или переключение булевого флага.

#### 5.7.6. Экран статуса внешнего GPS-приемника

- `Btn A`: возврат на `Telemetry Overview`.
- `Btn B`: обновление статуса или переключение детализации отображения.
- `Btn C`: переключение между кратким и расширенным видом диагностических данных.

### 5.8. Поведение интерфейса

- Интерфейс должен оставаться работоспособным при непрерывном приеме `CRSF`.
- Переключение экранов должно происходить без заметных задержек.
- При отсутствии данных от `CRSF` или `GPS` пользователь должен видеть понятный статус ошибки или отсутствия сигнала.
- Экран `Link Statistics` должен обновляться в реальном времени без остановки приема `CRSF`.
- Экран параметров симуляции не должен останавливать прием `CRSF` и отправку телеметрии при редактировании значений.
- При изменении источника GPS-телеметрии данные на экране должны обновляться в соответствии с новым активным источником без перезагрузки интерфейса.
- Поведение кнопок должно быть максимально единообразным между экранами, чтобы пользователь не переучивался при переходе между режимами.
- Операции `Save JSON` и `Load JSON` не должны нарушать прием `CRSF` и не должны приводить к потере отклика UI более чем на кратковременную операцию выбора команды.

### 5.9. Web UI

`Web UI` должен дублировать логические экраны LCD, но быть более удобным для работы на телефоне или ПК.

Минимальные требования к представлению:

- страница `CRSF Channels` должна показывать все каналы одновременно;
- страница `Link Statistics` должна показывать все параметры uplink/downlink одновременно;
- страница `Telemetry Overview` должна показывать все основные блоки телеметрии без необходимости пролистывать LCD-страницы;
- страница `Manual Telemetry` должна позволять быстро редактировать поля через формы;
- страница `Simulation Parameters` должна позволять быстро редактировать параметры и управлять профилями;
- страница `GPS Status` должна показывать диагностические данные в расширенном виде.

Минимальные требования к взаимодействию:

- `Web UI` должен поддерживать обновление данных без полной перезагрузки страницы;
- пользователь должен видеть статус соединения, актуальность данных и ошибки операций;
- изменения, внесенные в `Web UI`, должны применяться к общей конфигурации так же, как изменения с LCD;
- LCD и `Web UI` не должны расходиться по логике экранов и именам полей.

## 6. Нефункциональные требования

- Приложение должно стабильно работать на `ESP-IDF` без зависаний при непрерывной работе.
- Логика приема `CRSF`, передачи телеметрии и отрисовки UI должна быть разделена на независимые модули.
- Конфигурация пользователя должна храниться в энергонезависимой памяти.
- Параметры симуляции должны сохраняться и загружаться из `JSON`-файла на `SDCard`.
- `Web UI` не должен нарушать прием `CRSF`, отправку телеметрии и локальную работу LCD.
- Система должна корректно запускаться после включения питания без внешнего вмешательства.

## 7. Предлагаемая структура модулей

Для последующей реализации проект должен быть разделен минимум на следующие подсистемы:

- драйвер/модуль приема и парсинга `CRSF`;
- модуль формирования и передачи `CRSF telemetry`;
- модуль хранения конфигурации;
- модуль работы с `SDCard` и `JSON`-профилем симуляции;
- модуль работы с LCD;
- модуль пользовательского интерфейса;
- модуль `Wi-Fi` и встроенного `Web UI`;
- модуль ручного ввода телеметрии;
- модуль GPS-приемника;
- модуль симулятора GPS.

Для модулей `crsf_rx` и `crsf_tx` допускается использование или адаптация библиотеки `CRSFforArduino` в качестве основы реализации.

## 8. Критерии приемки

Проект считается соответствующим требованиям, если выполняются все условия:

1. Устройство собирается и запускается в среде `ESP-IDF`.
2. На `M5Stack Basic` отображаются значения каналов от подключенного `ELRS receiver` с именами `Ail`, `Elv`, `Thr`, `Roll`, `Aux1...Aux12`.
3. Пользователь может открыть экран `Link Statistics` и видеть на нем актуальные параметры uplink/downlink.
4. Пользователь может переключаться между экраном каналов и экраном телеметрии.
5. Пользователь может открыть экран обзора телеметрии, экран ручного ввода, экран параметров симуляции и экран статуса GPS.
6. Пользователь может выбрать один из трех источников GPS-телеметрии: ручной ввод, внешний GPS, симулятор.
7. Система передает по `CRSF` как минимум следующие типы телеметрии: `GPS`, `Attitude`, `Barometric Altitude`, `Battery`, `Flight Modes`.
8. В режиме ручного ввода пользователь может изменить телеметрические значения с LCD-интерфейса.
9. На экране параметров симуляции пользователь может настроить и запустить генерацию координат.
10. Пользователь может сохранить параметры симуляции в один из нескольких `JSON`-профилей на `SDCard` и затем загрузить выбранный профиль обратно.
11. В режиме внешнего GPS устройство принимает координаты от `M5Stack Mini GPS/BDS Unit (AT6558)` через `software UART` на `GPIO21/GPIO22` и отправляет их через `CRSF`.
12. `ELRS receiver` работает через `UART2` на `GPIO16/GPIO17`.
13. В режиме симуляции устройство генерирует координаты и отправляет их через `CRSF`.
14. Навигация по всем экранам и редактирование параметров выполняются тремя кнопками `Btn A`, `Btn B`, `Btn C` в соответствии с описанной схемой.
15. Пользователь может подключиться к `Web UI` по `Wi-Fi`, видеть те же логические экраны, что и на LCD, и изменять параметры более удобным способом.
16. При потере сигнала `CRSF`, ошибке `GPS`, отсутствии свежих `Link Statistics`, ошибке `Web UI` или отсутствии `SDCard` интерфейс показывает диагностический статус, а приложение не зависает.

- `BTN_A_LONG`;
- `BTN_B_LONG`;
- `BTN_C_LONG`.

Обработка кнопок должна строиться через очередь событий, а не через прямую логику внутри обработчика GPIO.

Требования к обработке кнопок:

- антидребезг должен выполняться программно;
- короткое нажатие должно быть базовым поддерживаемым действием;
- вся обязательная навигация должна оставаться доступной только на коротких нажатиях;
- обработчик кнопок не должен напрямую менять экран, он должен публиковать событие в UI;
- UI-модуль должен принимать решение о переходе между экранами и изменении значений.

### 9.4. Модель данных телеметрии

В проекте должна быть единая агрегированная структура телеметрических данных.

Минимальный состав общей телеметрии:

- блок `gps`:
  - `latitude`;
  - `longitude`;
  - `gps_altitude_m`;
  - `ground_speed_kmh`;
  - `heading_deg`;
  - `satellites`;
  - `fix_valid`;
  - `source`;
- блок `attitude`:
  - `pitch_deg`;
  - `roll_deg`;
  - `yaw_deg`;
- блок `barometric_altitude`:
  - `baro_altitude_m`;
- блок `battery`:
  - `voltage_v`;
  - `current_a`;
- блок `flight_mode`:
  - `mode_name`;
- `timestamp_ms`;

Требования к модели:

- ручной ввод, внешний GPS и симулятор должны обновлять только блок `gps` или соответствующие ручные блоки в общей структуре;
- перед отправкой в `CRSF` данные должны нормализоваться в один формат;
- активный источник GPS-телеметрии должен определять, какой модуль имеет право обновлять блок `gps`;
- блоки `attitude`, `barometric_altitude`, `battery` и `flight_mode` на первом этапе должны редактироваться вручную и храниться независимо от GPS-источника.
- поле `flight_mode.mode_name` на первом этапе должно принимать только значения `Angle Mode`, `Horizon Mode`, `Acro Mode`.

Отдельно в состоянии приложения должна существовать структура `link_statistics` со следующими полями:

- `uplink_lq_percent`;
- `uplink_snr_db`;
- `active_antenna`;
- `rf_mode`;
- `uplink_tx_power`;
- `downlink_rssi_dbm_neg`;
- `downlink_lq_percent`;
- `downlink_snr_db`;
- `timestamp_ms`.

Проект рекомендуется реализовать в виде следующих модулей:

  - хранение общего состояния;

  - прием данных от `M5Stack Mini GPS/BDS Unit (AT6558)` через `software UART` на `GPIO21/GPIO22`;

  - дополнительный разбор `GSA` и `GSV` для экрана `GPS Status`;

  - хранение параметров симуляции;

  - инициализация `Wi-Fi`;

  - встроенный HTTP-сервер;
  - выдача страниц `Web UI`;
  - передача актуального состояния в браузер;

- `ui`:
  - отрисовка экранов;
  - обработка событий кнопок;
  - навигация;
- `input`:
  - драйвер кнопок;
  - генерация событий `BTN_*`;
- `storage`:
  - сохранение конфигурации и ручных параметров в `NVS`;
  - загрузка конфигурации при старте;
- `display`:
  - низкоуровневая работа с LCD;
  - базовые примитивы отрисовки текста и индикаторов.

Допускается использовать или адаптировать библиотеку `CRSFforArduino` как основу для `crsf_rx` и `crsf_tx`.
Это инженерный вывод из источника: библиотека ориентирована на `Arduino`, но заявляет поддержку `ESP32`, поэтому для проекта на `ESP-IDF` может потребоваться адаптационный слой.
При использовании библиотеки необходимо учитывать ее лицензию `AGPL-3.0`.

### 9.7. Разделение задач `FreeRTOS`

Минимально рекомендуемая схема задач:

- `task_crsf_rx`:
  - прием UART-данных от `ELRS receiver` на `UART2`;
  - разбор кадров `CRSF`;
  - обновление `RX Channels` и `Link Statistics`;
- `task_gps_rx`:
  - прием данных от `M5Stack Mini GPS/BDS Unit (AT6558)` через `software UART` на `GPIO21/GPIO22`;
  - парсинг и публикация GPS-данных;
- `task_ui`:
  - обработка очереди UI-событий;
  - отрисовка экрана;
- `task_web_ui`:
  - обслуживание HTTP-сервера;
  - доставка состояния в `Web UI`;
  - обработка команд из браузера;
- `task_telemetry_tx`:
  - отправка телеметрии по `CRSF` с заданным периодом;
- `task_simulator`:
  - генерация координат при активном режиме симуляции.

Требования к задачам:

- прием по UART не должен блокироваться отрисовкой экрана;
- тяжелые операции отрисовки не должны выполняться в ISR;
- обмен между задачами должен происходить через очереди, события или защищенное общее состояние;
- период отправки телеметрии должен быть настраиваемым или вынесенным в константу;
- операции чтения и записи `JSON` на `SDCard` не должны блокировать критичный прием `CRSF` по UART.
- работа `Web UI` не должна блокировать критичный прием `CRSF` по UART.

### 9.8. Логика выбора источника GPS-телеметрии

В системе должен быть ровно один активный источник GPS-телеметрии:

- `GPS_SOURCE_MANUAL`;
- `GPS_SOURCE_EXTERNAL_GPS`;
- `GPS_SOURCE_SIMULATOR`.

Правила выбора источника:

- при переключении источника предыдущий источник теряет право обновлять блок `gps` в рабочей телеметрии;
- ручной источник использует последние сохраненные вручную GPS-значения;
- внешний GPS обновляет блок `gps` только при наличии валидных данных;
- симулятор обновляет блок `gps` только в состояниях `Running` или `Paused`;
- в состоянии `Paused` координаты не изменяются, но последний набор данных остается доступным для передачи;
- при невалидных данных от внешнего GPS система должна отображать ошибку, но не падать.

### 9.9. Поведение симулятора

Симулятор должен реализовывать следующие состояния:

- `SIM_STOPPED`;
- `SIM_RUNNING`;
- `SIM_PAUSED`.

Переходы состояний:

- `SIM_STOPPED -> SIM_RUNNING` по команде `Start`;
- `SIM_RUNNING -> SIM_PAUSED` по команде `Pause`;
- `SIM_PAUSED -> SIM_RUNNING` по команде `Resume`;
- `SIM_RUNNING -> SIM_STOPPED` по команде `Stop`;
- `SIM_PAUSED -> SIM_STOPPED` по команде `Stop`.

Требования к поведению:

- при `Start` симулятор должен начать с заданных стартовых координат;
- при `Pause` последние вычисленные координаты должны сохраняться;
- при `Stop` активный прогон завершается, но параметры симуляции не сбрасываются;
- команда `Reset` должна возвращать текущие координаты к стартовым значениям;
- команда `Save JSON` должна записывать текущие параметры симуляции в `JSON`-файл на `SDCard`;
- команда `Load JSON` должна читать параметры симуляции из `JSON`-файла на `SDCard` и применять их к текущей конфигурации;
- расчет движения должен выполняться с учетом скорости, курса и интервала обновления.

### 9.10. Формат `JSON`-профиля симуляции

Для параметров симуляции должен использоваться `JSON`-файл на `SDCard`.

Минимальные требования:

- каталог профилей по умолчанию: `/sdcard/crsf-display/profiles/`;
- профиль по умолчанию: `/sdcard/crsf-display/profiles/default.json`;
- должна поддерживаться работа с несколькими профилями симуляции;
- каталог должен создаваться автоматически при возможности записи;
- если файл отсутствует, приложение должно продолжать работу без остановки;
- если файл поврежден, пользователь должен видеть ошибку загрузки, но приложение не должно зависать.

Минимальный состав полей `JSON`:

- `version`;
- `start_latitude`;
- `start_longitude`;
- `altitude_m`;
- `speed_kmh`;
- `heading_deg`;
- `update_interval_ms`;
- `satellites`;
- `fix_valid`.

### 9.11. Сценарий запуска системы

После включения питания система должна выполнить следующую последовательность:

1. Инициализация `NVS`.
2. Загрузка сохраненной конфигурации.
3. Инициализация LCD и кнопок.
4. Инициализация и монтирование `SDCard`.
5. Загрузка последнего выбранного `JSON`-профиля симуляции, а при его отсутствии загрузка профиля по умолчанию, если файл доступен.
6. Инициализация `UART2` для `CRSF` / `ELRS receiver`.
7. Инициализация `software UART` для `M5Stack Mini GPS/BDS Unit (AT6558)` на `GPIO21/GPIO22`.
8. Инициализация `Wi-Fi` и встроенного HTTP-сервера `Web UI`.
9. Инициализация глобального состояния приложения.
10. Запуск задач `FreeRTOS`.
11. Открытие стартового экрана `CRSF Channels`.
12. Начало приема `CRSF` и готовность к передаче телеметрии.

### 9.12. Минимальный состав конфигурации в `NVS`

В энергонезависимой памяти должны храниться:

- последний выбранный источник GPS-телеметрии;
- последние значения ручной телеметрии для `GPS`, `Attitude`, `Barometric Altitude`, `Battery`, `Flight Modes`;
- пользовательские настройки отображения каналов;
- пользовательские настройки периода отправки телеметрии, если они будут доступны в UI;
- пользовательские настройки `Wi-Fi` и `Web UI`, если они будут доступны в интерфейсе;
- путь к последнему использованному `JSON`-файлу симуляции на `SDCard`.
